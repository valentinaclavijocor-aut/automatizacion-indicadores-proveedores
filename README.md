# Automatización de Indicadores para Proveedores

Proyecto desarrollado en el programa **EstudIA**, basado en un reto empresarial de **Industrias Haceb**.

## Descripción del proyecto

El proyecto busca mejorar el proceso de comunicación y consulta de indicadores de desempeño de los proveedores nacionales de Industrias Haceb.

Se propone desarrollar una plataforma web que permita centralizar la información, facilitar su consulta y automatizar las notificaciones mensuales.

## Objetivo

Diseñar e implementar un Producto Mínimo Viable (MVP) que permita:

- Administrar y publicar indicadores de proveedores.
- Consultar indicadores mediante un portal web seguro.
- Garantizar que cada proveedor acceda únicamente a su información.
- Consultar indicadores de períodos anteriores.
- Enviar notificaciones automáticas por correo electrónico cuando existan nuevos indicadores disponibles.
- Reducir tareas manuales y errores en la distribución de información.

## Alcance del MVP

El MVP contará con:

1. **Panel administrativo Haceb:** gestión y publicación de indicadores.
2. **Portal de proveedores:** acceso autenticado y consulta de información propia.
3. **Base de datos:** almacenamiento de proveedores, indicadores e históricos.
4. **Notificaciones:** envío automático de correos al publicar nuevos indicadores.
5. **Pruebas:** validación del funcionamiento y de las restricciones de acceso.

Se utilizarán datos simulados para demostrar el funcionamiento. La integración directa con Power BI dependerá de los accesos y permisos disponibles y no forma parte del alcance inicial obligatorio.

## Metodología de trabajo

- Desarrollo colaborativo mediante GitHub.
- Gestión de actividades mediante GitHub Issues y Projects.
- Uso de una rama independiente para cada tarea.
- Integración de cambios mediante Pull Requests.
- Revisión de los cambios por otro integrante del equipo.
- Uso de tecnologías gratuitas y open source.

## Reglas de colaboración

1. **Está prohibido realizar cambios directamente en la rama `main`.**
2. Cada integrante debe trabajar en una rama independiente, asociada a un Issue.
3. Los cambios deben presentarse mediante un Pull Request.
4. Cada Pull Request debe ser revisado por al menos otro integrante antes de integrarse.
5. No se deben aprobar Pull Requests sin revisar los cambios.
6. Las tareas deben mantenerse actualizadas en el tablero de GitHub.
7. No se deben subir contraseñas, credenciales ni información sensible al repositorio.
8. Los integrantes deben respetar las actividades y responsabilidades asignadas.

## Flujo de trabajo en GitHub

1. Seleccionar el Issue asignado.
2. Crear una rama a partir de `main`.
3. Realizar los cambios correspondientes.
4. Crear un Pull Request hacia `main`.
5. Solicitar revisión a otro integrante.
6. Corregir las observaciones, si existen.
7. Integrar los cambios después de su aprobación.
8. Actualizar el estado del Issue en el tablero.

## Estados del tablero

- **Backlog:** actividades identificadas para realizar posteriormente.
- **Todo:** actividades preparadas y asignadas.
- **In Progress:** actividades en desarrollo.
- **In Review:** actividades pendientes de revisión.
- **Done:** actividades finalizadas y verificadas.
